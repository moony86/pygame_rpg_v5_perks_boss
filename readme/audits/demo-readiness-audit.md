# فحص جاهزية ديمو BlueCube — 2026-10-22

الحكم: أساس تقني صالح للاستمرار، وجاهز لاختبار مغلق، لكنه يحتاج إصلاحات عرض وتوجيه وتغليف قبل ديمو عام. لا يوجد مبرر تقني مثبت لاستبدال Pygame قبل النشر.

## ما اختُبر فعلياً

- التشغيل على Python 3.12.7 وpygame-ce 2.5.7 الموجودين على الجهاز.
- اجتازت أدوات headless_checks جميع مجموعات الفحص الـ23، وانتهت بـHEADLESS_CHECKS_OK.
- إرسال حدث New Run إلى InputSystem نقل الحالة إلى HUB.
- إرسال Enter في PAUSED أبقى الحالة PAUSED، خلافاً لنص الشاشة.
- إنشاء صور مباشرة بواسطة Game.draw لحالات القائمة، Hub، الغرفة، القتال، الكروت، Pause، وBoss في debug_screenshots/demo_audit/.
- محاكاة غرفة عادية 600 خطوة × 1/60: 8 أعداء عند النهاية، متوسط update+draw = 10.6ms، وp95 = 18.48ms. رفعت صحة اللاعب في الذاكرة لضمان استمرار الملاحظة؛ رقم الصحة في صورة القتال ليس bug في اللعبة.
- اختبار الضغط المرفق: 100 عدو base = 69.3 إطار/ثانية مكافئ؛ 200 = 41.8؛ 300 Engineer = 29.1؛ Vampire = 25.5؛ Ninja = 26.4؛ Gunslinger = 37.0. قياسات headless على هذا الجهاز، وليست اختبار النسخة المبنية على جهاز نظيف. الغرف الفعلية تضبط active_cap بين 10 و15 تقريباً، لذا لا تعمم نتائج الضغط على الديمو كله.
- شُغلت نافذة اللعبة، لكن أداة تصوير سطح المكتب فشلت مرتين بمهلة capture. لم تكتمل تجربة WASD والتصويب اليدوية، ولم يُلعب Run كامل بصورة طبيعية. الصور محفوظة من renderer الحقيقي مع تهيئة حالات الاختبار، وليست screenshots لتجربة يدوية أو mockups.

## جودة المحرك والبنية

إيجابيات: فصل entities/systems/ui/definitions، حالات واضحة، كاش وصور spritesheets، enemy/projectile pools، spatial grid وLOD، أدوات profiling، اختبارات آلية، وأدوات تطوير داخلية. تحجيم viewport يحافظ على نسبة الشاشة ويحوّل إحداثيات الماوس.

نقاط صيانة: game.py يجمع أجزاء كبيرة من update/draw والتنسيق؛ تعريفات كثيرة وألوان ومقاسات مبعثرة؛ الواجهة تعتمد مواضع ثابتة وخط نظام Arial؛ لا يوجد dependency manifest واضح لتثبيت بيئة تطوير قابلة لإعادة الإنتاج. لا حاجة لإعادة كتابة شاملة قبل الديمو؛ إصلاح المشكلات المرئية وإكمال التحقق من النسخة الموزعة أهم.

## أدوات GUI الموجودة والخيارات

المشروع يحتوي بالفعل Dev Workspace عبر F12 في وضع التطوير: Overview, Gameplay, Builds, Tuning, Waves, Assets, Audio, Benchmark, Logs. يوجد RoomAuthoring لتحريك/تحجيم عناصر مع grid/snap وتصدير JSON، وRoomLoader للتحقق والمعاينة والتطبيق. هذه أدوات محدودة وليست محرر محرك كامل.

حدود حقيقية: reload_tuning يعيد False ولا يعيد تحميل القيم؛ Save Snapshot يسجل القيم، وPreview Load يعرضها ولا يطبقها. بعض المتغيرات مستوردة كقيم ثابتة وتتطلب إعادة تشغيل/ربطاً إضافياً. Clear Perks يمسح العدادات فقط، ولا يعكس تلقائياً جميع effects المطبقة، لذلك لا يصلح وحده كبداية اختبار build نظيفة.

pygame_gui مكتبة لبناء لوحات وأزرار وقوائم داخل Pygame، وليست محرراً يحوّل اللعبة تلقائياً إلى drag-and-drop. Tiled محرر خرائط يمكن ربط مخرجاته بمحمل للمشروع. Godot يوفر محرر مشاهد وواجهات متكاملاً، لكن استخدامه يتطلب نقل اللعبة وإعادة ربط أنظمتها؛ ليس فتح ملفات Python الحالية ومتابعة العمل مباشرة.

المراجع: https://pygame-gui.readthedocs.io/en/latest/ ، https://doc.mapeditor.org/ ، https://docs.godotengine.org/en/stable/getting_started/step_by_step/nodes_and_scenes.html

1. إصلاح المثبت، Pause، قص الوصف، HUD، وخريطة التنقل.
2. إرشاد بداية مختصر: الحركة، التصويب/الإطلاق، Dash، E، هدف الغرفة والباب، واختيار Perk.
3. تثبيت دورة ديمو واضحة من New Run إلى نهاية Stage وReplay.
4. توحيد الأصول واستكمال رسومات الكروت والأرضيات والأبواب ووضوح تحذيرات هجمات الأعداء.
5. بناء نسخة release جديدة، واختبارها على جهاز نظيف مع شاشات 1080p و720p وصوت مغلق/مفعّل ونافذة متغيرة.
6. اختبار مستخدمين جدد بلا شرح، ومراقبة: هل دخلوا أول غرفة؟ هل فهموا الهجمات/الكروت/الأبواب؟ هل أرادوا إعادة الجولة؟
